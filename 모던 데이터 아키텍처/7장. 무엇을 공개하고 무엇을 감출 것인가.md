# 7장. 무엇을 공개하고 무엇을 감출 것인가

> **2부 · 경계** — 어디에 선을 긋고 누가 책임지는가  
> 4장 · 5장 · 6장 · **7장**

떼어내기로 한 서비스가 있다.

그런데 코드를 뒤져 보니  
다른 팀 여러 곳에서 그 서비스의 테이블을  
직접 조회하고 있다.

테이블 이름 하나만 바꿔도  
어디가 깨질지 알 수 없는 상태다.

도메인을 잘 나누면 곧바로 현실적인 문제가 생긴다.

> 다른 도메인의 데이터가 필요하면 어떻게 하지?

이 장에서는 경계를 넘는 방법을 다룬다.

핵심은 하나다.  
내부 데이터 모델과 외부 공개 계약을 나누는 것이다.

모놀리스에서 서비스를 떼어내는 중이라면  
이 장이 가장 먼저 쓰인다.

---

## 1. 다른 도메인이 데이터를 필요로 한다면

도메인을 잘 나누면  
다음 문제가 생긴다.

> 다른 도메인의 데이터가 필요하면 어떻게 하지?

예를 들어 출금에서  
주문 데이터가 필요하다고 해보자.

가장 쉬운 방법은

```mermaid
flowchart LR
    n0["출금"] --> n1["주문 DB 직접 조회"]
```

다.

처음에는 편하다.

하지만 출금 시스템이 주문 DB의

테이블 구조,  
컬럼,  
JOIN 관계

까지 알게 된다.

결국 두 도메인이 다시 강하게 결합된다.

---

## 2. 공개 인터페이스를 만든다

대신 주문 도메인이  
외부에 사용할 수 있는 계약을 제공할 수 있다.

```mermaid
flowchart LR
    WD["출금 Domain"]

    subgraph ORDER["주문 Domain"]
        CONTRACT["공개 인터페이스<br/><br/>판매자 ID<br/>주문 금액<br/>주문 시간<br/>포인트 유형"]

        subgraph INNER["🔒 내부 구현"]
            T1["order"]
            T2["order_detail"]
            T3["point_usage"]
            T4["…"]
        end

        CONTRACT --> INNER
    end

    WD -->|"공개된 계약만 사용"| CONTRACT

    style CONTRACT fill:#e8f4ff,stroke:#4a90e2,stroke-width:2px,color:#1a1a1a
    style INNER fill:#f5f5f5,stroke:#999,stroke-dasharray: 5 5,color:#1a1a1a
```

출금 도메인은 이 네 가지만 알면 된다.

내부에서 몇 개의 테이블을 JOIN했는지는  
알 필요가 없다.

책에서는 이러한 역할을  
`Data Provider`라는 표현으로 설명할 수 있지만,

이 용어 자체가 DDD의 필수 표준 용어는 아니다.

핵심은 이름이 아니라

> **내부 데이터 구조와  
> 외부 공개 계약을 분리한다.**

는 원칙이다.

---

## 3. API만이 유일한 방법은 아니다

도메인 간 데이터를 전달한다고 해서  
항상 HTTP API만 사용해야 하는 것은 아니다.

상황에 따라 여러 방법을 사용할 수 있다.

```text
API

Domain Event

Message Broker

CDC

Data Pipeline

Data Product

Read Model
```

중요한 것은 어떤 기술을 사용하느냐보다

> **누가 생산자이고  
> 누가 소비자이며  
> 데이터의 의미와 책임이 어디에 있는가**

가 명확해야 한다는 것이다.

---

## 4. 중간 시스템이 있다고 잘못된 구조는 아니다

데이터가 반드시 생산자에서 소비자로  
직접 전달되어야 하는 것은 아니다.

예를 들어 다음 구조도 충분히 가능하다.

```mermaid
flowchart LR
    n0["주문 Domain"] --> n1["Kafka"] --> n2["출금 Domain"]
```

또는

```mermaid
flowchart LR
    n0["운영 DB"] --> n1["CDC"] --> n2["데이터 플랫폼"] --> n3["분석용 Data Product"]
```

도 가능하다.

문제는 Kafka나 파이프라인 자체가 아니다.

문제는 이런 구조다.

```mermaid
flowchart LR
    n0["원본 DB"]
    n1["ETL"]
    n2["공통 DB"]
    n3["또 다른 ETL"]
    n4["중간 DB"]
    n5["소비 시스템"]
    n6["#quot;그래서 이 데이터의 주인이 누구지?#quot;"]
    n0 --> n1
    n1 --> n2
    n2 --> n3
    n3 --> n4
    n4 --> n5
    n4 --> n6
```

중간 시스템 때문에

데이터 출처,  
의미,  
소유권

이 흐려지는 것이 문제다.

따라서 정확한 원칙은 다음과 같다.

> **중간 시스템을 쓰지 말라는 것이 아니라  
> 중간 시스템 때문에 데이터 소유권과 의미가  
> 사라지게 만들지 말자.**

---

## 5. 소비자가 사용하기 좋은 데이터를 제공한다

내부 테이블을 그대로 공개하는 것보다  
소비자가 필요한 데이터 모델을 제공하는 것이 좋다.

예를 들어 출금에서는

```text
판매자 ID
주문 금액
포인트 유형
출금 가능 여부
```

가 중요할 수 있다.

반면 분석에서는

```text
날짜
판매자
구매자
주문 금액
주문 시간
```

이 필요할 수 있다.

따라서 하나의 원천에서  
여러 형태의 데이터가 나올 수 있다.

```mermaid
flowchart TD
    d["주문 Domain"] --> a["분석용 Data"]
    d --> b["실적용 Data"]
    d --> c["집계용 Data"]
```

하지만 소비자마다  
모든 요구를 별도 모델로 만들어주는 것도 좋지 않다.

생산자가 소비자 요구에  
지나치게 끌려다닐 수 있기 때문이다.

따라서

**재사용성**과  
**소비 편의성**

사이의 균형이 필요하다.

---

## 6. 타 도메인 DB 직접 접근은 무조건 금지인가?

원칙적으로 비즈니스 로직에서

```text
출금 → 주문 내부 테이블 직접 수정

```

같은 구조는 피하는 것이 좋다.

도메인 경계를 무너뜨리기 쉽기 때문이다.

하지만

> 다른 도메인 테이블을  
> 어떤 상황에서도 읽으면 안 된다.

는 절대 법칙은 아니다.

예를 들어

분석,  
통계,  
CQRS Read Model,  
Materialized View

처럼 여러 도메인의 데이터를  
결합해야 하는 목적이 있을 수 있다.

따라서 더 정확한 원칙은

> **도메인의 핵심 비즈니스 로직이  
> 다른 도메인의 내부 구현에 직접 의존하지 않게 한다.**

라고 이해하는 것이 좋다.

---

## 7. 도메인 안은 강하게, 도메인 사이는 느슨하게

지금까지 배운 원칙을  
가장 간단하게 표현하면 다음과 같다.

```mermaid
flowchart TD
    subgraph d1["주문 Domain · 내부는 높은 응집도"]
        a1["주문 규칙"]
        a2["주문 Application"]
        a3["주문 Data"]
    end
    subgraph d2["출금 Domain · 내부는 높은 응집도"]
        b1["출금 규칙"]
        b2["출금 Application"]
        b3["출금 Data"]
    end
    d1 -- "명확한 계약" --> d2

```

즉,

> **경계 안은 밀접하게 만들고  
> 경계를 넘을 때는 느슨하게 만든다.**

이 원칙이 DDD와 데이터 도메인을  
관통하는 핵심이다.

4장부터 7장까지를 연결하면 다음과 같다.

```text

       ↓

       ↓
변경 영향도가 커진다.
       ↓
좋은 소프트웨어 설계 원칙을 적용한다.

높은 응집도
낮은 결합도
명확한 인터페이스
       ↓
비즈니스 기준으로 경계를 찾는다.
       ↓
DDD를 활용한다.

Domain
Subdomain
Bounded Context
Ubiquitous Language
       ↓
비즈니스 역량과 시스템을 연결한다.
       ↓
데이터에도 책임 경계를 만든다.
       ↓

       ↓

       ↓

       ↓

```

## 10. 2부의 핵심

2부에서 가장 중요한 것은  
시스템을 많이 쪼개는 기술이 아니다.

다음 세 가지를 명확하게 만드는 것이다.

> **무엇을 책임하는가?**

> **어떤 데이터를 책임하는가?**

> **다른 영역과 어떤 계약으로 연결되는가?**

따라서 데이터 도메인이란

> **DB를 기준으로 데이터를 나누는 것이 아니라  
> 비즈니스 책임을 기준으로 경계를 만들고  
> 각 영역이 자신의 데이터에 책임을 가지게 하는 것**

이라고 이해하면 된다.

하나의 저장소와 하나의 DB를 사용한다고 해서  
도메인 중심 설계를 할 수 없는 것도 아니다.

반대로 마이크로서비스와 DB를 수십 개로 나누었다고 해서  
좋은 도메인 설계가 되는 것도 아니다.

결국 중요한 것은 물리적인 분리가 아니다.

```text
명확한 비즈니스 경계

       +

명확한 데이터 소유권

       +

경계를 넘는 명시적인 계약

```

이 세 가지가 함께 있어야 한다.

그리고 여기에

```text
자율적인 도메인 운영

       +

전사 공통 거버넌스

```

가 더해질 때  
규모가 커져도 관리할 수 있는  
데이터 아키텍처로 발전할 수 있다.
